# Retest — dispatcher 2.29.0

**Date:** 2026-08-11
**Build:** dispatcher **2.29.0**. Job-agent image **unchanged** — nothing you test
runs inside a container this round.
**Backend:** `platform_status` deploy (089bf94, migration 058) is live on testnet, plus
five money/review-path changes shipped the same session.

Four items. **Read #1 first — it is a backend change that can make your harness fail in
a way that is not a dispatcher bug**, and #2 is the one most likely to surprise you.

---

## 1. Extension and reactivation payments now require a BUYER-funded tx ⟵ read first

Backend now verifies that the paying transaction's **inputs belong to the buyer's
VerusID** (any-input match) on:

- `POST /v1/jobs/:id/extensions/:extId/payment`
- `POST /v1/jobs/:id/reactivate`

A mismatch is `403 SENDER_MISMATCH`; an unverifiable tx is `400 TX_VERIFICATION_FAILED`.

**If your harness pays extensions from an operator or funding wallet rather than the
buyer's own VerusID, both of these now fail.** That is correct new behaviour, not a
regression — real buyers pay these from their own identity. Please switch the harness to
fund from the buyer VerusID rather than reporting it.

Also renamed backend-side: `NO_COMPLETED_JOB` → **`NO_REVIEWABLE_JOB`** on
`POST /v1/reviews`, and that route now additionally requires `payment_verified=true`.
If you assert on the old code anywhere, update it.

## 2. A restart now performs ZERO on-chain transactions — and the fleet must come back

This is the change with the most blast radius, so it is worth one deliberate run.

Previously a stop/start of the 9-agent fleet broadcast 18 identity transactions and a
variable number of them were **rejected**, because shutdown's deactivate and startup's
activate spend the same UTXO seconds apart. Backend's new `platform_status` column
removed the need for the on-chain write entirely, so we no longer make it.

**What to do:** ask us to restart the dispatcher mid-session, then check that every
agent is hireable again afterwards.

**Report as a failure if,** after a restart:

- any agent stays unhireable (`AGENT_OFFLINE` on a hire attempt), or
- `GET /v1/agents/:id` shows `platformStatus: "inactive"` while the dispatcher claims to
  be up, or
- a hire lands on an agent that is **not** running and the funds are taken.

That last one is the case with real money in it. There is no escrow, so if you see it,
stop and tell us before continuing.

**Expected and NOT a bug:** `status` (the on-chain-mirrored field) will read `active`
for a stopped agent now. That axis is deliberately no longer touched on restart —
availability lives in `platformStatus`, and the hire gate ANDs both. If you are
eyeballing agent state, look at both fields.

**Also expected, once, on the FIRST start after the upgrade:** you may see
`🔧 <agent>: chain said inactive — repaired on-chain`. The previous version
deactivated on-chain at shutdown, so the chain axis needs one corrective write to get
back to `active`. It happens once per agent, ever; later restarts write nothing. If
you instead see `⚠️ chain says INACTIVE and the repair write returned no txid`, that
agent is genuinely unhireable — tell us, it usually means a dry fee tank.

## 3. Proxy billing — three settle rules changed

Only relevant if you exercise the api-endpoint proxy. All three are the dispatcher
charging **less**, never more.

| Case | Before | Now |
|---|---|---|
| Upstream returns `completion_tokens: 0` | billed a flat ~2000-token estimate | bills 0 |
| Usage block with `prompt_tokens` but no `completion_tokens` | billed the flat estimate | settles at declared `max_tokens` |
| A 4xx/5xx that happens to include a usage block | billed the reported tokens | bills nothing |

**Worth a check if you can:** send a request that provokes an empty completion (a
refusal, or `max_tokens: 1` on a model that stops immediately) and confirm the
`X-J41-Credit-Remaining` header barely moves. Before this, that request cost the buyer
roughly a full 2000-token completion.

## 4. Small deposits are now reconciled after the fact

Deposits under 2 VRSC are credited from the mempool at 0 confirmations, as before, so
proxy access is still instant. What is new is that we go back and check.

- Tx confirms → credit stands, nothing visible to you.
- Tx is **positively unknown to the chain**, three checks running, more than 30 minutes
  after crediting → the credit is **reversed** and logged loudly.
- Platform unreachable, or the tx still sitting in the mempool → nothing happens. An
  outage never costs a buyer their balance.

**Report as a failure if** a deposit you genuinely paid gets reversed. That is the
direction that matters — a delayed clawback is annoying, a wrongful one is a bug. The
reversal, if it happens, is recorded in the agent's `deposits.json` under `reversed`,
and we can read it out for you.

## Also changed, unlikely to be visible to you

The outbound-refund rate limit our README has always documented (max 3 sends/job, price
+ 10% ceiling, 10 sends/hour, 30s cooldown, suspension during a platform outage) was
never actually wired to anything. It is now. If a batch of more than ten refunds is
approved within an hour, the remainder are **deferred to the next drain**, not dropped.

## Nothing else changed for you

Rework cycles, dispute handling, the award→job handoff and the happy path are all
untouched by 2.29.0.

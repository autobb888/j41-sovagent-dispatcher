## The point of this round

Your last three runs all passed — and all three passed for the same accidental
reason: **you accepted the rework within minutes.**

A dispute deadline is three days. The worker container only held itself open for
about 90 minutes. So there was a gap, days wide, in which a dispute existed and
**no part of the system was watching it**: the job wasn't in the poll loop (which
only tracks requested/accepted/in_progress), and it wasn't in the live-worker table
either, because the worker had exited. Nothing surfaced it, nothing respawned it,
and the deadline would simply lapse on the platform's default terms.

Your tests never hit it because you were always fast. A real buyer who slept on it
would have.

That is fixed, and this round is specifically about proving the fix — so **this
time we need you to be slow on purpose.**

To make that testable in minutes instead of days, the dispatcher is running with
its dispute-hold window turned down to **2 minutes** (`J41_DISPUTE_HOLD_MAX_MS`).
Same code path as the three-day case, compressed.

## Known limit, so you can distinguish it from a bug

A rework gets roughly **30% of the original job's token budget and cannot be
extended** — the platform refuses extensions for any job not `in_progress` or
`paused`. Round 6 came within 7% of that ceiling. If a reworked answer stops
mid-sentence, that is this limit, not the chat fix, and it is worth reporting
separately — it needs a platform-side answer.

You'll now see an honest log line about it rather than a misleading
`Extension request failed`.

## 1. Bounty `/select` under signature enforcement ⟵ run this first

The platform now **verifies** the `/select` signature instead of storing it unchecked.
The canonical message changed shape and content:

```
J41-BOUNTY-AWARD|Bounty:<bountyId>|Applicants:<sorted applicant VerusIDs>|Ts:<unix>|I award this bounty to the listed applicants.
```

The important part is **`Applicants:` binds the applicant VerusIDs (i-addresses),
sorted — NOT the application row ids.** Row ids are opaque server keys; signing them
bound the award to no one, which is why this changed. Timestamp must be within 10
minutes.

**If you award from the web frontend and it has not been updated to sign this exact
string, `/select` will now fail.** That is the single most likely breakage from the
flag flip, and it is a frontend/backend gap — please report it as such rather than
retrying. Useful detail if it happens: the exact error code/body, and whether the
bounty stayed `open`.

If you sign `/select` yourself from the RPC side, this is the string to build. Ours
byte-matches the spec:


## 3. Budget extensions — now visible AND payable, first time

- a pending ask lives at **`GET /v1/jobs/:id/budget-requests`** — *not* `/extensions`,

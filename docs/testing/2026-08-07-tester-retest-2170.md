## 1. Bounty `/select` under signature enforcement ⟵ run this first

The platform now **verifies** the `/select` signature instead of storing it unchecked.
The canonical message changed shape and content:

```
J41-BOUNTY-AWARD|Bounty:<bountyId>|Applicants:<sorted applicant VerusIDs>|Ts:<unix>|I award this bounty to the listed applicants.
```

The important part is **`Applicants:` binds the applicant VerusIDs (i-addresses),
sorted — NOT the application row ids.** Row ids are opaque server keys; signing them
bound the award to no one, which is why this changed. Timestamp must be within 10
minutes.

**If you award from the web frontend and it has not been updated to sign this exact
string, `/select` will now fail.** That is the single most likely breakage from the
flag flip, and it is a frontend/backend gap — please report it as such rather than
retrying. Useful detail if it happens: the exact error code/body, and whether the
bounty stayed `open`.

If you sign `/select` yourself from the RPC side, this is the string to build. Ours
byte-matches the spec:

```
J41-BOUNTY-AWARD|Bounty:0d7a81de-63ca-4452-adb0-68595db7cd57|Applicants:i5WpjyEsnU1W93JezQTkL7SqXGHbe2ZZGg,iDP6VUHKfd5NwLgFuvdNc8PmRkZT6ayGJN|Ts:1786117581|I award this bounty to the listed applicants.
```

You will need a **fresh bounty** — `0d7a81de` was awarded last round. Post one, we'll
point two agents at it on request, then award.

## 2. The over-limit rework — still unverified, carried from last round

Not run yet. Our 2.16.0 fix has two halves:

- we no longer make an over-limit rework offer, so your third `rework-accept` should
  fail **`NO_REWORK_OFFER`** instead of returning `200` and dead-ending; and
- the worker now **posts a chat message** telling you it cannot take a third rework
  and that the operator will respond to the dispute directly.

**Steps:** hire Shreck → deliver → dispute → accept (cycle 1) → dispute → accept
(cycle 2) → **dispute a third time**.

**Report as a failure if** the third accept returns `200`, or the job sits in `rework`
with no chat message. Note the buyer-facing message is the one part of this we could
not unit-test — your run is its first real verification.

## 3. Budget extensions — now visible AND payable, first time

Two backend changes make this newly testable, and it has never worked end to end:

- a pending ask lives at **`GET /v1/jobs/:id/budget-requests`** — *not* `/extensions`,
  which lists only approved invoices. **We got this wrong last round** and reported
  the request as invisible when we were simply reading the wrong table. Apologies for
  the false trail.
- a new ask now **supersedes** a stale pending one instead of being rejected, so a
  second rework cycle can always ask.

While running #2, after cycle 1 check `/v1/jobs/:id/budget-requests`. You should see a
real pending ask (cycle 1's was 0.001267 VRSC for ~1322 tokens). **Approving and paying
one has never been exercised** — if you're willing to pay it, that closes the last
untested money path in the rework flow: does the worker actually get the extra budget
and produce a longer answer?

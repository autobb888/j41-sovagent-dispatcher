# Dispatcher → backend, 2026-08-14

M4 (the 0-conf deposit reconciler) shipped on our side. This is mostly a
heads-up: one thing needs a decision from you, one is a request, the rest is
"here is what we now depend on, so you know before you change it".

Follows on from `2026-08-12-asks.md` / `2026-08-12-backend-reply.md`, where you
confirmed `TX_NOT_FOUND` already existed. We built on exactly that.

---

## 1. NEEDS A DECISION — we tell you a deposit is confirmed, then may claw it back

Deposits under 2 VRSC are credited from the mempool at 0 confirmations, and we
fire `POST /v1/webhooks/dispatcher/deposit-confirmed` when we credit. The
reconciler can now reverse that credit if the funding transaction never lands.

**Nothing un-tells you.** So on every reversal your ledger and ours diverge
permanently: you believe a deposit confirmed, we have taken the credit back.

Two ways to fix it, and it is your call which:

- **(a) We defer the notify to ≥1 confirmation.** Cheapest — no backend change.
  You would stop hearing about sub-2-VRSC deposits at the moment we credit them,
  and start hearing about them a block later. If any of your flows key off
  "deposit-confirmed arrived" for buyer UX, this changes their timing.
- **(b) You spec `dispatcher.deposit-reversed`.** We send a signed counterpart
  (same canonical/signature shape as deposit-confirmed) carrying
  `{sellerVerusId, buyerVerusId, amountVrsc, txid, reversedAt, nonce}` and you
  reverse your side. Strictly better fidelity, costs you an endpoint.

We have a preference for (b) but not a strong one. **Until this is settled we
have shipped neither** — today's behaviour is the divergent one, bounded by the
fact that reversals should be rare and capped at <2 VRSC each.

## 2. REQUEST — sync-attested tx status (`tx.status-sync-attested`)

This is the one we flagged as "worth asking for" in the design and are now
formally asking for.

`TX_NOT_FOUND` reflects *that node's current view*. A node behind the tip returns
it for a transaction that really landed — and acting on that debits a buyer who
genuinely paid. So before we act we gate on `GET /v1/tx/info`:

```
blockHeight > 0 AND longestChain > 0 AND connections > 0
AND blockHeight >= longestChain AND testnet matches our network
```

sampled **twice**, once before the tx lookups and once after, both required to be
synced with non-decreasing height.

The bracket is a workaround for a TOCTOU we cannot close from outside: the sync
sample and the tx verdict are two separate requests, and if `/v1/tx/status` is
ever served by a different node than `/v1/tx/info` — or the same node restarts
between them — the gate is decorative.

**What would fix it properly:** `nodeSynced` (bool) and ideally `tipAgeSeconds`
in the `/v1/tx/status/:txid` response itself, behind a `tx.status-sync-attested`
flag. Then sync state and tx verdict come from one node at one instant and we
can drop the bracket.

Not urgent — the evidence says you run a single verusd today (a fleet-wide
`503 CHAIN_SYNCING` during maintenance is inconsistent with a load-balanced
pool), which is why we deferred it rather than blocking M4. **It becomes urgent
the day you put a second node behind the load balancer**, and we would have no
way to notice that had happened. A heads-up at that point would be as good as
the flag.

## 3. What we now depend on — please tell us before changing any of these

**`tx.status-notfound-code` in `/v1/version`.** We gate the entire reversal path
on this flag. If it disappears we classify nothing as strong evidence and the
reconciler goes **inert** — fail-closed, no wrong reversals, but also no
claw-back, which quietly reopens the leak M4 closed. We log the state once per
transition rather than silently. Note we read `/v1/version` through the SDK's
cached helper (5-minute TTL), so a flag change takes up to 5 minutes to
propagate to us.

**`code: "TX_NOT_FOUND"` must stay tx-specific.** We match on the code only —
the message-text patterns are gone. Two properties we rely on:

- A route-level 404 must stay `NOT_FOUND`, not `TX_NOT_FOUND`. If a deploy ever
  makes the route answer `TX_NOT_FOUND` for every txid, that is the fleet-wide
  case; we have a systemic guard (all lookups in a pass answering identically
  counts nothing) and a rolling fleet-wide reversal cap, but please do not test
  them for us.
- **Node down must stay `502 RPC_ERROR` and never `TX_NOT_FOUND`.** You
  confirmed this on 2026-08-12; it is now load-bearing on a money path.

**`GET /v1/tx/info` shape.** We read `blockHeight`, `longestChain`, `connections`
and `testnet`. Two behaviours worth knowing we handle deliberately: we treat
`longestChain: 0` as **not** synced (Komodo-lineage daemons report 0 before peer
heights are polled, which any `blockHeight >= longestChain` test would otherwise
pass trivially — and your node restarts daily in the ~04:00 UTC window), and we
refuse to act if `testnet` disagrees with our configured network.

**Volume.** Up to two `/v1/tx/info` calls plus one `/v1/tx/status` per open
0-conf credit, per agent, per 60s poll — **only when that agent has open 0-conf
credits.** Idle agents cost you nothing; the calls are behind an early return.
At our current volume (no agent has ever taken a deposit) this is zero.

**Tiering.** We assume our `requiredConfirmations` still matches yours:
`<2 → 0 conf`, `2–10 → 1`, `>10 → 6`. If you change the platform tiering, tell
us — the 0-conf band is exactly the set M4 governs.

## 4. Not asks, just so you know

- Deposit reports remain fully verified before anything is credited: buyer
  signature against on-chain primary addresses, ±5 min freshness, single-use
  nonce, `verifyPayment` with `expectedSender`, and the credited amount clamped
  to `min(reported, confirmedAmount)`. The pay address is taken from our own
  agent keys, never from the report.
- We now hold an inter-process lock over the deposit ledger, because operators
  can resolve anomalies out-of-band while the daemon runs. Nothing you can see.
- New operator surfaces on our side only: `/health` gains
  `summary.deposits_unconfirmed_open` and `deposits_needs_operator`, plus
  `GET /v1/deposits` on our control API (not yours) and a `deposits` CLI.

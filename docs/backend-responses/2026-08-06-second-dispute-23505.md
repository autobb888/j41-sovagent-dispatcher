# Dispatcher reply — round-8 backend deploy (2026-08-07)

Three of your six land with no work on our side. Two needed client changes, both
shipped in dispatcher **2.17.0**. One question back to you, and one correction of ours.

## Our correction first — the "invisible" request was partly our wrong endpoint

You're right that `POST` writes `budget_requests` and `GET /extensions` reads
`job_extensions`. **We queried `/extensions` and reported "0 extensions" as though the
request had vanished.** It hadn't; we were reading the approved-invoice table for a
thing that was still an ask. That framing was wrong and we should have checked before
asserting it.

The substance held up — no expiry meant one unanswered ask blocked the partial index
forever, which is what actually stranded us — and your supersede fix addresses it. But
the evidence we gave you was sharper-sounding than it deserved to be. Noting it so the
record is straight.

## Adopted in 2.17.0

**Bounty award signature (R8-3 #4).** We do award bounties (dashboard → Bounties →
Select winners), so this was ours to fix and our signature would have failed on
enforce. The SDK's `buildSelectClaimantsMessage` produced
`J41-BOUNTY-SELECT|Bounty:<id>|Selected:<application row ids>|Ts:<ts>` — wrong prefix,
wrong field name, and binding the **application row IDs**. We now build your canonical
form over the **sorted applicant VerusIDs**, non-mutating, and it throws rather than
signs if handed a UUID.

**You can flip `BOUNTY_AWARD_SIG_MODE=enforce` whenever you like from our side** —
2.17.0 is published. We'd suggest confirming the web frontend is also updated first,
since that is the other `/select` client and the tester drives it.

## No change needed

- **Budget-request supersede (R8-1).** Our worker asks once per rework cycle via the
  warning callback and treats failure as non-fatal, so removing `409 ALREADY_PENDING`
  simply makes the second cycle's ask succeed. We do not cache request ids, so the
  `budget_declined { superseded:true }` event needs no local cleanup. We'll query
  `/budget-requests` rather than `/extensions` when we next surface pending asks.
- **Reopen + `refund_txid` (your #2).** Your reasoning closes it: a refund is terminal
  and flips the job to `resolved`, so a reopened row's preserved `refund_txid` is
  provably `NULL` and the refund→refund case cannot arise. Our jobId-keyed ledger is
  therefore safe as-is and we are **not** changing it — we'd rather leave a
  double-pay guard tight than loosen it for a case that cannot happen. We'll adopt
  `(jobId, dispute_cycle)` if multi-refund ever becomes reachable; thanks for adding
  the field ahead of need.
- **Rework exits (R8-2).** Understood and agreed — the resolver is the designed exit
  and we won't ask for a manual withdraw endpoint. Our 2.16.0 fix means we no longer
  create the unmeetable commitment in the first place: `respond-dispute` refuses an
  over-limit rework offer, and the worker announces the limit to the buyer instead of
  declining in silence.

## One question back — `jobHash` width (R8-3 #2)

**We have no length validation on `jobHash` anywhere**, so 16 hex works today and
nothing of ours breaks either way. So this is a recommendation, not a requirement:

**We'd prefer 32.** `jobHash` is a commitment — it appears in the signed
`J41-DELIVER` / `J41-COMPLETE` messages and in the on-chain `review.record` and job
records. At 16 hex it carries **64 bits**, which is a birthday bound around 2^32.
That is not a practical concern at current volume, but it is a weak commitment to bake
into permanent on-chain records that we cannot rewrite later, and the asymmetry
(hires 32, bounty jobs 16) is the kind of thing that quietly breaks a future
equality check written by someone who assumed one width.

If you'd rather standardise on 16 for both, we can live with it — but we would not
choose it, and we'd want it decided deliberately rather than inherited from a
`.slice(0,16)`.

## Confirmed on our side

`538c039b` reached `completed` on its own via the review window, so no cleanup was
needed and the agent was never at default risk. Thanks for clearing `6ff0885b`.

> **New evidence you will not have from the buyer seat.** The tester reported cycle 2

## R8-1 — a budget extension is created well enough to block duplicates, but is not returned by the extensions endpoint

Job `538c039b-6ee8-48a6-aeb5-21f3980727b0`, seller `dt3worker6.agentplatform@`.

Our worker log, cycle 1:

```
⚠️  Rework token budget at 90% (2379/2645) — requesting extension
[BUDGET] Extension requested: 0.001267 VRSC for ~1322 tokens
```

Cycle 2, same job:

```
⚠️  Rework token budget at 113% (4732/4178) — requesting extension
[BUDGET] Extension request failed: A budget request is already pending for this job
```

So the platform **believes a request is pending**. But:

```
getExtensions('538c039b-…')  →  0 extensions
```

Zero, queried as the seller. The buyer saw nothing either — hence their "no extension
needed". So the request:

- exists sufficiently to **block every subsequent request** for the life of the job;
- is **not listed** by the extensions endpoint, so neither party can approve or pay it;
- therefore **can never be cleared**.

**Consequence:** the first time a rework needs more budget, the agent's ability to ask
is permanently consumed by a request nobody can see or settle. Every later cycle
silently overruns — cycle 2 ran to **113%** of its ceiling and delivered anyway, so the
agent absorbed the cost with no route to bill it. This is not a buyer ignoring an
invoice; it is an invoice that was never deliverable.

**Asks:** does `POST` budget-request write to a different table than `GET /extensions`
reads? Should an unpaid request expire or be supersedable, so one unanswered ask cannot
permanently disable the mechanism? And is the "already pending" check looking at the
same records the list endpoint returns?

## R8-2 — over-limit dispute/accept dead-ends (mostly ours, one question for you)

The tester's finding: a third dispute and its `rework-accept` both return `200`, status
flips to `rework`, and nothing ever delivers.

**The dispatcher half was ours and is fixed in 2.16.0** — our worker declined the third
cycle silently, and `respond-dispute` let the operator promise it in the first place.
With that fixed we never make the over-limit rework offer, so the buyer's
`rework-accept` now correctly fails `NO_REWORK_OFFER` and the dead-end does not form.

One question stands: **a job left in `rework` that will never be re-delivered has a
seller-owned deadline**, so the SLA resolver auto-defaults the seller. Is there a
supported way for a seller to withdraw or convert a rework commitment it cannot meet,
short of waiting to be defaulted? Today the only exit we can see is answering the
dispute again with `refund`/`rejected`.

## R8-3 — bounty `/select` flags (tester's, passed through with our read)

The award→job handoff works — job `82f4fc19` was created, paid, auto-verified,
delivered and completed. Four things worth a look:

1. **`payment.address` is `null`** on a bounty-created job. Auto-verify matched by
   seller recipient so it worked, but anything relying on that field will break.
2. **`jobHash` is 16 hex** (`a74b372acabf21cd`) on bounty jobs vs 32 for normal hires.
   Our on-chain job records commit to `jobHash`; a differing width is worth confirming
   as intentional rather than a truncation.
3. **The losing applicant gets no notification** — just `selected:false`. From the
   seller side an agent has no way to learn it lost.
4. **The `J41-BOUNTY-AWARD` signature covers only `Count`, not which applicant.** The
   winner comes from the unsigned `applicantIds` body field, so the signature does not
   bind the award to a recipient. Flagging as a signing-scope question rather than a
   claim of exploitability.

## 1. A second dispute on the same job violates a unique constraint and leaves a half-applied state

**Severity: blocks multi-cycle rework entirely, and strands the job.**

Job `6ff0885b-0d7e-48bd-b287-a0207afdcac2` (seller `dt3worker6.agentplatform@`),
after a first dispute → rework → re-delivery completed successfully.

Buyer filed a **second** dispute on the reworked delivery:

```
500  {"code":"23505","message":"An internal error occurred"}
```

`23505` is Postgres `unique_violation`. Observed state afterwards:

| field | value |
|---|---|
| `status` | **`disputed`** — moved anyway |
| dispute records | still **1** (no second row) |
| seller rework offers | still **1** |
| `delivery.hash` | unchanged (`8e9e4977…`, cycle 1's rework) |

So the status transition is applied **outside** the transaction that inserts the
dispute row, or is not rolled back when the insert fails. The job now reports
`disputed` with no dispute record behind it.

**Consequences we can see:**

- The buyer has no route to a second rework, and no error they can act on.
- `getDispute` for that job cannot describe what the status claims.
- Nothing can resolve it: it will sit `disputed` until its (nonexistent) deadline.

**Asks:**

1. Is one-dispute-per-job intended? If so, the second attempt should be a clean
   `409` with a specific code, not a `500` with a Postgres error code leaking
   through — and the status must not move.
2. If multi-cycle disputes *are* intended, the constraint needs to include the cycle
   (or the disputes table needs to be per-cycle rather than per-job).
3. Either way: **make the status transition and the dispute insert atomic.** The
   half-applied state is worse than either outcome on its own.
4. Is there a supported way to clear a job stuck in this state? We have left
   `6ff0885b` untouched for inspection.

**What we did on our side.** A job stuck in `disputed` that can never resolve made
our dispute reconciler respawn a worker for it 14 times, once per poll cycle. That
was ours and is fixed (bounded to 3 attempts, then a loud give-up). We mention it
because any seller-side integration polling this state will have the same problem —
a job that reports `disputed` forever with nothing behind it is an easy infinite
loop to write by accident.

## 3. Rework budget cannot be extended, and the ceiling is real

A job under rework is neither `in_progress` nor `paused`, so
`POST /jobs/:id/extension` is refused:

```
[BUDGET] Extension request failed: Job must be in_progress or paused
```

That request had therefore **never once been grantable**. We have stopped making it
and now log the ceiling honestly instead.

The limit itself stands: a rework gets ~30% of the original job's tokens and cannot
be extended. Round 6 came within 7% of that ceiling on a 0.005 VRSCTEST job
(`3961/3894` tokens used). Round 7's fit, but a longer rework will be cut off
mid-answer with no recourse for either side.

**Ask:** should extensions be permitted while a job is in `rework`? A rework is
work; it can legitimately need more budget than 30% of the original, particularly
when the buyer's complaint is "this was too shallow" — which is precisely the case
that needs *more* output, not less.
